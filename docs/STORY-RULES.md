# Правила репозитория для чата «Сюжет»

Составлено 16 ноября 2026 по словам владельца `[владелец:О-12]`–`[владелец:О-18]`; исправлено по независимой проверке того же дня. Порядок работы оркестра по сюжету — в `docs/STORY-ORCHESTRA.md`. Правки, которые нужны в инструкции проекта, — в `docs/INSTRUCTION-CHANGES.md`.

Старшинство: прямые слова владельца в чате → инструкция проекта и план (при их расхождении действует план) → `CLAUDE.md`, этот файл и `docs/STORY-ORCHESTRA.md` → `docs/CONVENTIONS.md` → навыки плагина. Где эти два файла уточняют навык плагина для работы чата «Сюжет», действуют они. Метки источников и ворота G1–G8 из `docs/CONVENTIONS.md` ни один из них не ослабляет.

Пока правки из `docs/INSTRUCTION-CHANGES.md` не внесены, там, где инструкция проекта спорит с работой этого чата, действует запись владельца из `decisions/OWNER.md`; где записи нет — вопрос владельцу `[студия]`.

## 1. Назначение

Чат «Сюжет» пишет полный сюжет игры по обновлениям, события, квесты одиночные и с друзьями, диалоги, а также оформление того, что видит и слышит игрок: сцены, облики, эффекты, музыку `[владелец:О-16]`. Сначала прописываются сюжет, сроки и шаги его синхронизации с функционалом игры по датам этапов плана и обновлений `[владелец:О-17]`. Основа — лор-библия плана `[владелец:О-15]`.

Репозиторий — мастерская чата. Канон игры остаётся в плане. Чат «Сюжет» план не правит `[владелец:О-15]`, поэтому его результат попадает в план только подсказкой, которую принимает владелец `[студия]`. Раздел плана «Сюжет и часы» прямо говорит, что историю разрабатывают вне плана, а план хранит только решения `[canon:stages.md#Этап 2: MVP, 21–27 ноября]`.

Инструменты Roblox Studio технически видны в сессии через приложение на компьютере владельца. Дирижёр их не загружает и не вызывает. Роль получает запрет в тексте запроса на любом пути запуска — и агентом плагина, и запасным путём (навык `orchestra`, раздел «Как звать роль»): по канарейке в `docs/SETUP.md` роли плагина помечены «все инструменты». Если вызов всё же случился, это пишется первой строкой отчёта владельцу.

## 3. Ветка и коммиты

- Рабочая ветка — `claude/Сюжет` `[владелец:О-12]`. Держать одну ветку на все шаги — правило студии `[студия]`: шаги различаются папками `drafts/<ГГГГ-ММ-ДД>-<слово>/`, а не ветками. Навык `orchestra` с версии 0.2.0 берёт ветку из `CLAUDE.md`.
- Два шага одновременно можно вести только если у них разные папки и ни один не меняет файлы другого. Стыки между шагами решает дирижёр, а не роли.
- В `main` всё уходит запросом на слияние по вехе (например, «Арка v1 принята», «Пакет окна А готов»). Сливает владелец.
- Один коммит — одно действие: бриф, черновик роли, проверка, решение продюсера, перенос в `bibles/`, слова владельца. Сообщение — одна строка по-русски: что сделано и какой шаг.
- После каждого законченного куска — отправка ветки на GitHub, чтобы обрыв сессии не стёр работу.
- Не коммитятся `node_modules`, файлы SoundFont, ключи, токены, файлы больше 2 МБ без решения владельца.

Папки `bibles/story/…` создаются, когда в них впервые переносится принятое. Пустых заготовок не держим.

## 5. Как сюжет становится каноном

Статусы из `docs/CONVENTIONS.md`, раздел 1, плюс один промежуточный для сюжета. Статусы называются словами, а не номерами:

- `черновик` — файл роли в папке шага.
- `проверен` — APPROVE контролёра.
- `принят в репозитории` — решение продюсера по классам А и Б; документ переезжает в `bibles/story/`, метки `[предложено]` сохраняются.
- `выбран владельцем` — владелец ответил на развилку в чате; ответ записан в `decisions/ESCALATIONS.md` и даёт метку `[владелец:E-N]`. Это решение владельца, но ещё не канон плана.
- `принято владельцем` — владелец принял подсказку в плане. Только это канон. Отметку в шапке документа ставит дирижёр отдельным коммитом.

Строить в Studio можно только то, что `принято владельцем`. Это делает чат «План» обычным порядком плана, а не этот чат.

Пакет для плана (`drafts/<шаг>/plan-proposal.md`) готовит дирижёр по навыку `orchestra`. Подсказки в раздел «Лор-библия» кладёт сам чат «Сюжет»; остальные разделы — чат «План» по пакету `[владелец:E-2]`. Копия пакета кладётся в документы проекта: `claude/Сюжет — пакет <дата>.md`, чтобы чаты без GitHub её прочитали.

## 6. Начало и конец сессии

В начале:

1. `git pull` ветки `claude/Сюжет`; дерево чистое.
2. Версия снимка (`canon/SNAPSHOT.txt`) против `data.rev` плана: дешёвое чтение по навыку `qv-plan-reader`. Если план ушёл вперёд, — изменения через `sinceRev`; если изменённые блоки лежат в разделах, которые попадают в снимок (`tools/canon_snapshot.py`), — новый снимок скриптом, отдельным коммитом, до любых черновиков. Полная выгрузка плана идёт в файл, а не в контекст.
3. Прочитать `BACKLOG.md` (группа З), открытые вопросы в `decisions/ESCALATIONS.md`, последние записи `decisions/LOG.md`.
4. Если владелец в чате сказал новое, — сначала запись в `decisions/OWNER.md`.

В конце: статусы задач в `BACKLOG.md` с датой, коммит, отправка ветки, отчёт владельцу по виду из `docs/STORY-ORCHESTRA.md`.

## 7. Чего чат не делает

- Не правит план и не пишет в Roblox Studio.
- Не придумывает цены, состав магазина, шансы и схему сохранений. Не загружает ничего в Roblox. Не тратит деньги.
- Не фиксирует ответы на загадки, пока владелец не решил иначе (ворота G1).
- Не сдвигает даты этапов и окон плана. Сроки сюжета внутри студии предлагает, даты плана берёт из снимка.
- Не пишет противоречия лора и игры в журнал плана: они идут в `drafts/_findings/` и в пакет для плана.
- Не выдаёт решение продюсера или своё за слова владельца.
